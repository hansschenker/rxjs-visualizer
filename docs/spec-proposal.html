One TestScheduler frame is one column

Inside testScheduler.run() a marble character is one virtual frame and one frame is one millisecond. The visualizer already draws time as x = startX + t · scale with one shaded band per step, so a spec maps onto it by choosing the unit: step = 1 frame, scale = 30 px. Rows stay what they are today, one per marble line. Below is your debounceTime spec drawn that way, paused at frame 7.

The spec, as written in rxjs

it('should debounce values by 2 time units', () => {
  testScheduler.run(({ hot, time, expectObservable, expectSubscriptions }) => {
    const e1 = hot('  -a--bc--d---|');
    const e1subs = '  ^-----------!';
    const expected = '---a---c--d-|';
    const t = time('  --|');                       // 2 frames

    expectObservable(e1.pipe(debounceTime(t))).toBe(expected);
    expectSubscriptions(e1.subscriptions).toBe(e1subs);
  });
});

What the scheduler actually recorded

Run through the real TestScheduler with a capturing assert callback instead of a test framework. The operator did the work; nothing was reimplemented.

e1 (hot)     → a@1  b@4  c@5  d@8  complete@12
subscription → ^@0 … !@12
actual       → a@3  c@7  d@10  complete@12
expected     → a@3  c@7  d@10  complete@12   ✓ match

Gotcha: the static TestScheduler.parseMarbles() reports frames ×10 (10, 40, 50 …) because the frame factor outside run() is 10. Parse and run inside run(), where a frame is 1 ms.

debounceTime(2) on the grid, paused at frame 7

source / actual value expected value (ring) debounce window (t = 2 frames) window cancelled by a newer value complete ▮ playhead · frames to its right are still in the future

Read it top to bottom in any frame: a value enters on the source lane, drops onto the operator lane and opens a window of t frames, and when the window closes an arrow drops the value onto the output lane. b's window is cut at frame 5 because c arrived inside it, which is the whole idea of debounce, and it is visible as a dashed stub ending in a cross. The output lane shows the expected marbles as rings and the actual ones as fills; a mismatch would be a ring without a fill or a fill without a ring, drawn in red.

How it plugs into the current code

  • Coordinates need no new rule. Today's renderer takes stepMs and timeScale; a spec page passes stepMs: 1 (one frame) and timeScale: 30. Bands, ruler and timeX() work unchanged. Only the marble size shrinks from 32 to 26 so two adjacent frames (bc) never overlap.
  • The scheduler supplies the data. new TestScheduler((actual, expected) => record(actual, expected)), then run the spec verbatim inside run(). The source marbles come from hot()/cold(), the actual output from the capture, the subscription log the same way. rxjs/testing is plain TypeScript with no Node dependency, so it runs in the browser.
  • State becomes frame-based. Instead of a column per source emission, the state holds lanes with events { frame, kind, value }, optional spans (subscription, window, cancelled window), a total frame count and a playhead. The reducer gets one new action, TICK, that advances the playhead; the reveal effect that already exists drives it.
  • Operator lanes are opt-in annotations. Source and output lanes are generic for any spec. The window lane is produced by a small per-operator annotator (debounceTime, auditTime, delay, throttleTime share one: "a duration that starts at an input frame"). Operators without a time component simply have no middle lane, and the arrow drops straight from source to output.
  • A third page, spec.html, next to the diamond and glitch pages. Later, a spec picker whose entries are the marble strings copied verbatim from the rxjs repo's spec files.

Choices to make

  • 30 px / 26 px marble (shown) or 40 px / 32 px marble, which keeps today's marble size and makes values easier to read but stretches a 13-frame spec to 520 px. The scale is one config value either way.
  • Playback speed. 400 ms per frame reads well for short specs; a scrubber on the ruler would help with long ones.
  • Mismatch styling. Rings without fills and fills without rings in red is the proposal; a failing spec would then look like its diff.
  • Where cancelled windows go. Dashed stub with a cross on the operator lane (shown), or fade them out entirely after the newer value arrives.

Recommendation: build spec.html around the real TestScheduler with stepMs: 1, timeScale: 30 and a 26 px marble, start with this debounceTime spec, and add the window annotator for the time-based operators first. The diamond page keeps its real-time mode; both share one coordinate rule.
